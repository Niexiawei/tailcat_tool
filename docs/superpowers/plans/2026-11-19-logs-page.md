# 统一日志（日志页 + 设备标签）实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 subagent-driven-development（推荐）或 executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）跟踪进度。
>
> **前置：** 依赖 `2026-11-19-appmeta-cache-page.md` 任务 1 的「管理入口骨架」（路由常量、侧栏设备列表之下的入口、`ContentTitle` 面包屑）。骨架没做之前不要开工。

**目标：** 设备页的「日志」标签与独立日志页**共用同一份实现**：一条按时间倒序的时间线，包含**应用自己的错误/警告**、通道日志、任务；支持设备 / 级别 / 时间段筛选与关键词模糊搜索，任务行可点开看输出。日志统一落 SQLite，重启后仍能查。**设备标签不删除**，它调同一个界面，只是把设备固定成它自己（`DeviceID = 本设备`）。

**架构：** SQLite 成为日志的**唯一真相**（页面不再读内存 `Session.Logs`）：新增 `logs` 表存应用与通道日志，任务仍以 `tasks` 表为准，页面用一条 `UNION ALL` 查询把三者合成时间线（`source` 区分 app / channel / task，`ref` 带上任务 id）。写入沿用现有的**非阻塞队列**（满了丢弃并计数，绝不阻塞界面）。`logView` 是唯一的日志界面：日志页与设备页「日志」标签都调它，标签那份传 `ShowDevicePicker: false` 并把设备钉死。

**技术栈：** Go 1.27.3、`modernc.org/sqlite` v1.62.0（bundled SQLite 3.54.1，已启用 FTS5，但本计划只用 `LIKE`，理由见「决策与代价」）、onevra `components`（`TableVirtualized` / `Select` / `Tabs` / `TextBox` / `Switch` / `Badge` / `Dialog`）、`ui.NewTester`。

**规格：** 用户 2026-11 的口头需求（「设备日志页 + 独立日志页整合在一起」「应用的错误或者警告日志也放进来」「支持时间段和模糊搜索」「日志存 sqlite 便于搜索」）；没有独立规格文档。裁决写进本文「决策与代价」，落地后同步进 `docs/architecture.md` §15 与 `docs/ui-and-console.md`。

## 全局约束

- 纯 Go、禁止 cgo；不引入新依赖（搜索用 `LIKE`，不引入 FTS5 表）。
- 依赖方向不变；`internal/app` 只调 `Manager` / `HistoryReader`，不碰 SQL。
- **所有进入日志的文本先过 `core.Redact(text, "")`**：应用级错误里可能出现 `tc...` 地址，`channel_logs` 原本已经脱敏，这里不能因为换了张表就漏掉。
- 写库不阻塞界面：沿用 `history.Store` 的队列（容量 256，满则丢弃并累加丢弃计数）。
- 查询一律带上限（默认 500 行）与时间下界；绝不允许「先拉全表再在界面过滤」。
- 保留期 30 天、上限 5 万行，打开时与每 1000 次写入后清理一次。
- **日志界面只能有一份实现**（`logView`），两个入口只传不同的过滤状态与选项；任何筛选/跟随/输出/清空行为只改一处。
- 面向用户的中文文案，测试逐字断言。
- GUI 一律优先 onevra `components`；行式元素 `FillWidth()`，**禁止** `Fill()`。
- 每个提交：`gofmt -w`、`go vet ./...`、`go test ./...` 全绿；用户可见改动同提交写进 `docs/CHANGELOG.md`。
- 分支 `feat/logs-page`。

## 审查重点（Review Focus）

1. **日志里不能出现连接地址**：应用级错误（`vm.FailText`、启动问题、托盘失败）以前只活在内存提示条里，现在要落盘；漏一次就是凭据进 SQLite（`TestAppLogTextIsRedacted`）。
2. **写日志不得阻塞界面**：`vm.FailText` 可能在界面线程上执行；写入必须走队列，队列满了丢日志而不是卡帧（`TestAppLogDoesNotBlockWhenTheQueueIsFull`）。
3. **迁移不得丢 `channel_logs` 老数据，且只能迁一次**：`PRAGMA user_version` 从 0 到 1，重复打开不能重复插入（`TestMigrationCopiesChannelLogsOnce`）。
4. **搜索不能把整张表读进内存**：单设备 30 天可能上万行；`LIMIT` 必须作用在过滤之后，被截断时页面要说「只显示最近 500 条」（`TestTimelineLimitAppliesAfterFiltering`）。
5. **设备页「日志」标签只能查自己**：它必须传 `DeviceID = 本设备`（不是 `nil`），否则会把别的设备与应用级日志混进来（`TestDeviceLogTabQueriesOnlyThatDevice`）。两个入口共用一份实现，也不得为了「顺手」分叉（`TestLogPageAndDeviceTabShareTheSameRows`）。
6. **跟随最新只查增量**：每 2 秒重查全量会让大库下界面抖动；跟随必须用 `Since = 最后一行的时间`（`TestFollowQueriesOnlyNewRows`）。
7. **`--demo` 下页面不能是空的**：演示环境没有历史库，必须注入一个内存版 recorder + reader，否则截图与人工验收都看不到内容（`TestDemoLogsPageHasRows`）。

```sql
CREATE TABLE IF NOT EXISTS logs (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  at          INTEGER NOT NULL,
  level       TEXT NOT NULL,      -- error | warn | info
  source      TEXT NOT NULL,      -- app | channel
  device_id   TEXT NOT NULL,      -- '' 表示应用日志
  device_name TEXT NOT NULL,
  text        TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS logs_at ON logs(at DESC);
CREATE INDEX IF NOT EXISTS logs_device_at ON logs(device_id, at DESC);
```

迁移（`Open` 里，写协程内执行）：

```sql
-- user_version 0 → 1，只跑一次
INSERT INTO logs(at, level, source, device_id, device_name, text)
SELECT at, 'info', 'channel', device_id,
       COALESCE((SELECT t.device_name FROM tasks t
                 WHERE t.device_id = channel_logs.device_id
                 ORDER BY t.started_at DESC LIMIT 1), ''),
       text
FROM channel_logs;
PRAGMA user_version = 1;
```

迁移后**不再写 `channel_logs`**（表保留，不删用户数据）。`RecordLog` 改写 `logs`（`level='info'`、`source='channel'`）。

查询（core 类型）：

```go
// TimelineEntry is one row of the log page: an app line, a channel line or a task.
type TimelineEntry struct {
	At         time.Time
	Level      LogLevel
	Source     LogSource // LogApp | LogChannel | LogTask
	DeviceID   uuid.UUID // uuid.Nil for app lines
	DeviceName string
	Text       string
	TaskID     uuid.UUID // set for LogTask; opens its output
}

// LogQuery selects a slice of the timeline. DeviceID nil means every device and
// app line; *uuid.Nil means only app lines.
type LogQuery struct {
	DeviceID *uuid.UUID
	Level    LogLevel
	Since    time.Time
	Search   string // space-separated terms, all must match
	Limit    int
}

type HistoryReader interface {
	Timeline(LogQuery) ([]TimelineEntry, error)
	TaskOutput(id uuid.UUID) (string, error)
}
```

SQL 用一条 `UNION ALL`，`logs` 与 `tasks` 各自过滤后再合并排序、最后 `LIMIT`：

```sql
SELECT at, level, source, device_id, device_name, text, ref FROM (
  SELECT at, level, source, device_id, device_name, text, '' AS ref FROM logs WHERE ...
  UNION ALL
  SELECT started_at, 'info', 'task', device_id, device_name,
         title || ' · ' || state, id FROM tasks WHERE ...
) ORDER BY at DESC LIMIT ?
```

任务侧的搜索同时匹配 `title` 与 `output`（`output` 只出现在 `WHERE`，不进 `SELECT`）。

### 验收

- `--demo`：页面有演示数据；四个筛选项各切换一次结果正确；任务行能打开输出；空态文案出现；设备页「日志」标签**只出现本设备的行**（应用级行不出现）。
- 真机：跑一次失败的任务（如 `pull` 不存在的路径）→ 日志页能搜到「失败」→ 点开看到 stderr；断网制造一次连接错误 → 应用级 error 行出现在「应用」筛选下。
- 重启应用：日志仍在（这是本计划的核心目的）。
- 老库升级：升级前把 `channel_logs` 填满 → 升级后日志页能看到那些行，且数据只出现一次。

### 风险

- 时间线完全依赖 SQLite 写入队列，界面比现在**慢一拍**（毫秒级，但不再是"发生即显示"）；跟随开关打开的体验接近现在。
- 两个入口共用一份实现，风险集中在“忘了固定设备筛选”：设备标签一旦传 `nil` 就会把全库日志灌进来。测试钉参数，不钉外观。
- 30 天 / 5 万行是硬编码常量；需要时再加设置项（不在本轮）。

## 决策与代价

| 决定 | 代价 |
|---|---|
| 两个入口（日志页 + 设备页标签）、**一份实现** | 设备标签也带筛选行，比原来的纯文本重；换来任何日志行为只改一处，两处不会各说各话 |
| SQLite 是日志的唯一真相，页面不再读 `Session.Logs` | 界面比事件慢一个队列周期；`--demo` 必须自带内存 recorder；换来重启后可见、可搜索，且不必维护"内存 + 库"两段拼接 |
| 新增 `logs` 表而不是给 `channel_logs` 加列 | 多一张表、多一次迁移；换来 `channel_logs` 老数据零风险（只读、不删、不写），迁移逻辑只在 `user_version` 0→1 跑一次 |
| 应用只把 **error / warn** 入库，成功提示不入库 | 用户看不到"我点过什么成功操作"；换来日志页不被「已复制」这类噪声淹没 |
| 搜索用 `LIKE '%kw%'`，不用 FTS5 trigram | 5 万行以上会明显变慢，只能靠保留期与时间范围兜住。**实测**（`modernc.org/sqlite` v1.62.0，bundled SQLite 3.54.1）：FTS5 与 `tokenize='trigram'` 都可用，中文子串 `MATCH '无法解析'` 能命中；但 trigram 索引约让日志体积翻倍、需要手动同步，而且**少于 3 个字的查询用不了索引**——用户搜「失败」正是 2 个字。所以先用 LIKE，把 FTS5 作为"实测慢到不可接受"时的升级路径 |
| 保留 30 天 / 5 万行，打开时与每 1000 次写入后清理 | 用户可能想查更早的记录（硬上限，无设置项）；换来库不会无限长大（按 200 B/行估算约 10 MB 封顶） |
| 清空只删 `logs`，不动 `tasks` | 用户可能以为"清空日志"把任务也清了；对话框里写明，且任务输出是排查依据，删掉更可惜 |
| 清空后不 `VACUUM` | `history.db` 文件不会变小（空间复用）；换来清空是瞬时的，不会卡住界面几十秒 |
| 侧栏入口排在「缓存管理」「DERP 地图」之前 | 侧栏顺序与"管理页"分组不完全一致（日志是浏览不是管理）；换来最常用的页面在最上面 |
| 设备标签固定 `DeviceID = 本设备`，因此看不到应用级日志 | 设备上出问题后，应用级错误要去日志页看；换来「这台设备的日志」名副其实，不混入全局事件 |
| 设备标签默认「跟随最新」开启，日志页默认关闭 | 两个入口默认值不同，需要在文档里写清；换来标签保持现在“贴底滚动”的手感，页面保持“静止查阅”的手感 |
